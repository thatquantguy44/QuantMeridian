# InventoryBallast guided showcase

**Status:** As-built local SIM presenter path for QuantMeridian spec013, 2026-10-18.

The QuantMeridian service loads InventoryBallast package `0.1.0` from reviewed main commit `a42dad30dc3ebb80d2790fd8701e621af0a35fcb` (InventoryBallast PR #40, engine spec0020 solver diagnostics; re-pinned 2026-10-19 from `bb425cac10d1da29e74fe8f854fd41b31f460773`, PR #39) and checks source fingerprint `ff61a5bc5ffb05379bb7f5a56c9f0b3f999811ee5f6d69875a77b0a2440c8b39` at readiness. The source is pinned, not followed by branch name. A separate QuantMeridian pin PR can be reverted independently of the showcase UI.

The new service endpoints enumerate three checked-in SIM books and run InventoryBallast's own deterministic `run_demo`. The terminal renders the engine's results and diagnostics in the guided base → shock → diagnose → repair → compare sequence. It does not calculate its own objective, allocation, binding status, ranking, or repair. The principal book's supply shock makes the `INV-AAA` inventory-balance row bind at 40 shares, versus 100 in base. The verified repair increases value and adds a new entity driver; matched and new entities stay distinct. The agency book shows owner economics and mandate disclosures. The prime book deliberately produces an infeasible shock, with no allocation, then a verified repair; the diagnosis exposes coverage and excluded-source evidence.

Every result exposes solve and verification status, objective when verified, termination reason, run and input hashes, and engine pin. Solver/formulation, binding rows, economic attribution, demand/flow, agency and prime disclosures are rendered from service artifacts. Stress outcomes preserve engine ranks only when status and independent verification permit a valid outcome. Production remains disabled by default; no G2D, G2E, or G3 gate is granted. The presenter banner and catalog label all data `SIM`.

The showcase books are LPs (variant `lp`, no integer variables); an earlier version of this note called them mixed-integer, which was wrong. With engine spec0020 the base step shows the principal book's LP sensitivity ranges from a separate ranging solve of the same request (`base_sensitivity`; the guided steps solve without ranging), and every result carries model statistics and phase timings. The prime book's diagnosis carries the engine's elastic infeasibility explanation: `no_relaxable_rows`, because the book has no utilization limit, the only rule the diagnostic may relax, so the infeasibility comes from hard client coverage. The explanation is not an IIS. The terminal never invents shadow prices or ranges. This is decision-support demonstration data, not a live recommendation.

Local golden service tests cover pin identity, the verified principal shock/repair, matched/new drivers, prime planned infeasibility and its explanation, the base-book ranges (route ALPHA's coefficient 10 × 0.025 / 360 within [10 × 0.015 / 360, +∞)), unknown books, auth and production gate. Browser viewport and keyboard walkthroughs still require a complete terminal checkout with npm dependencies and CI capacity.
